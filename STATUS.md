# Project Status: Prism

## Lifecycle

Active development at version 1.1.7. Development proceeds as continuous iteration driven by the operator's own hands-on use of a running instance: work is prioritized from gaps observed in day-to-day operation rather than from an external roadmap. Upgrade work keeps the clean architecture and takes the best current implementation, so legacy shapes are preserved only when explicitly requested.

Development Tier: MVP

## Deployment

Verified self-hosted deployment models:

- Root Docker Compose bundle (one Prism app image plus PostgreSQL, named volumes for data and config).
- Single app image (`docker build .`) with an external PostgreSQL.
- Local launcher (`./start.sh full|headless`) for development.

Prism runs as a personal deployment on a home LAN and is reached from that network. It is not exposed to the public internet and is not operated as a service for anyone else.

Development and deployment convenience is prioritized over data-security hardening: on this personal home-LAN deployment, the convenient path wins when the two trade off. Consistent with that posture, security controls stay optional and minimal (optional operator auth and proxy API keys, a plaintext bootstrap file, no TLS termination, operator-owned network exposure). The priority concerns security hardening; it does not by itself authorize destructive data resets or dropping the explicit-authorization-plus-backup bar for retained data, which remain governed by the policies below.

## Users

No external users. The single operator is the person running the home-LAN instance, with optional operator login and optional proxy API keys. Product direction comes from that operator's own usage experience.

## Data

- PostgreSQL holds management state, request logs, audit logs, usage events, and loadbalance events (partitioned retained tables plus live management tables).
- A plaintext bootstrap file (`config.json`, path set by `PRISM_CONFIG_PATH`) owns startup settings. The `runtime.transport` config section was removed outright (no compatibility shell) in v1.0.20: Prism no longer applies connection or timeout limits to outbound provider requests, and a leftover `runtime.transport` block fails startup with a readable migration error.
- models.dev catalog metadata is introduced by `000024_model_catalog_metadata.sql` as a purely additive migration: a `model_catalog_bindings` table (one optional management-only metadata row per model), optional `catalog_provider_id`/`catalog_model_id` columns plus a partial unique index on `pricing_templates`, and `revision_source`/`catalog_revision` evidence columns on `pricing_template_revisions`. All retained models, templates, revisions, references, and logs survive unchanged; catalog metadata never enters the runtime snapshot and its writes never invalidate planning. The models.dev binding surface has since been hardened without any migration: every write (bind/refresh/override/clear/unbind) takes the model row lock and then the binding row lock. Bind re-verifies the caller-confirmed Prism identity and catalog ETag; refresh re-verifies its catalog ETag plus the previewed binding coordinate/`updated_at`; sparse override confirms the displayed coordinate and merges over the locked current row; bulk override clear and unbind verify the confirmed coordinate/`updated_at` snapshot, with unbind idempotent once the row is gone. The stable `409 models_dev_model_changed`/`models_dev_binding_stale`/`models_dev_catalog_stale` conflicts write nothing, refresh commits are source-only UPDATEs, concurrent same-offering per-field overrides never lose updates, and a monotonic token helper advances `updated_at` even under a fixed clock. All `/api/models/{id}/catalog*` responses, and the model-detail GET while it still embeds the legacy models.dev catalog field, answer `Cache-Control: private, no-store`; the candidates endpoint publishes per-page `catalog_revision`/`fetched_at` snapshot evidence without fabricating a freshness enum. The model detail page composes both sources under a federated 外部目录来源 section with independent per-source loading/error/stale/empty surfaces.
- Terminal Target upstream model id decoupling is introduced by `000031_terminal_target_upstream_model_identity.sql` as a data-preserving migration: nullable `connections.upstream_model_id` (varchar(200)) is backfilled exactly from each owned connection's unique owner model current `model_id`, orphan rows keep NULL, multiple-owner anomalies abort migration, and nullable request-time snapshots on `request_logs` and `usage_request_events` leave every historical row unchanged. Clients keep addressing the stable entry `model_id`; each upstream attempt across every registered model-bound operation (OpenAI Chat/Responses/adjunct/Images, Anthropic Messages/Count Tokens, Gemini generate/stream/count, multi-target failover) rewrites the provider model identity to the selected target's frozen upstream ID, while logical attribution (`model_id`, `resolved_target_model_id`), capability checks, routing, pricing, custom-parameter priority, and provider response passthrough stay unchanged. Runtime planning excludes orphan connections and rejects any replacement snapshot containing an active owner-backed target with a missing or blank identity, preserving the last-good generation. Management semantics: create omission writes the owner model's current `model_id` explicitly; explicit null/blank/over-200-Unicode-character values are 422 field errors with zero writes; PATCH omission preserves and the field cannot be cleared; model rename never cascades; and copy preserves the source value. The runtime writer freezes the request-time snapshot onto every real upstream attempt row and the winner usage event; planning/admission/legacy/no-winner rows keep NULL without quarantine, and list, chain, exact detail, finalized summary (`final_upstream_model_id`), and CSV project stored evidence verbatim without inference. The frontend prefills the owner `model_id` with manual decoupling, hydrates edits, supports composite create and copy prefill, shows the identity on access targets, and renders a reasoned `—` for historical gaps on an optional hidden-by-default Requests column.
- Direct client-entry qualification is introduced by the additive `000032_model_direct_request_enabled.sql`: `model_configs.direct_request_enabled` is `BOOLEAN NOT NULL DEFAULT TRUE`, existing rows are backfilled to `TRUE`, and no retained model, access target, connection, request log, usage event, or directory binding is otherwise rewritten. Runtime planning keeps all enabled models for recursive Model Target routing but resolves client-bound operations only through direct entries; `/v1/models`, Pi export, route-witness setup roots/representatives, and proxy-key self-test selectors use the direct projection. Non-entry models remain valid Model Targets and expose an incoming-reference count plus an explanatory warning when unreferenced. The exact 12-entry/four-mapping reclassification ships as the tracked operator runbook at `docs/operations/direct-request-entry-reclassification.md` and SQL at `scripts/operations/direct-request-entry-reclassification.sql`, with `backend/tests/integration/direct_request_entry_reclassification_plan_test.go` as its tracked acceptance support. None is invoked by startup or applied automatically, and this task did not run the plan against the home-LAN instance.
- Output-rate evidence is introduced by `000030_output_delivery_rate_evidence.sql` as a purely additive migration: `output_rate_state`/`output_rate_reason`/`output_delivery_event_count`/`output_delivery_span_ms` on `request_logs` and `usage_request_events` with CHECK-guarded four-state evidence. The runtime classifies progressive visible text/tool-output delivery once per request (strict per-operation allowlists; ≥2 events and ≥50ms first-to-last span) and writes the same verdict to the final attempt row and the usage event. Every statistics and Requests read surface derives tok/s only from `state=measured` rows (`output_tokens * 1000.0 / output_delivery_span_ms`), so GLM-style buffered bursts, non-streaming responses, Images, failures, and evidence-insufficient requests no longer pollute the tok/s average; historical rows and legacy v2/provisional outbox payloads materialize as `unknown` (never quarantined), all request/token/cost/audit facts survive unchanged, and old TTFT-derived rate artifacts are retired from every mean.
- `000029_pricing_catalog_source_live_uniqueness` corrects the models.dev offering-uniqueness guard so it also excludes `deleted_at IS NOT NULL`. It is an index-definition-only, data-preserving migration: rebuilding the index scans `pricing_templates` but rewrites or removes no application row; a retired source-linked template keeps its coordinates and full revision history as provenance, and re-importing the same models.dev offering afterwards creates a new live template instead of failing. The template and revision read surfaces now project that provenance (`catalog_provider_id`/`catalog_model_id` on templates and paged list items, `revision_source`/`catalog_revision` on revisions and the current-revision DTO), a half-populated coordinate pair fails closed as `pricing_template_catalog_evidence_incomplete`, and `/api/pricing-templates/catalog/preview` plus `/commit` answer `Cache-Control: private, no-store` because previews carry state-bound catalog, template, and Terminal Target evidence that intermediaries must not retain. Any relevant pricing-state change invalidates the preview hash; unchanged template-only reuse remains idempotent with respect to template and target state rather than becoming a server-enforced one-time token, while the successful mutation route still advances its runtime planning-cache generations.
- The client model-config export (`/route/models/export`, backed by the fixed Pi-only routes `GET /api/models/exports/pi/source` and `POST /api/models/exports/pi/render`, both `M3`) generates the Pi 0.84.3 `prism-pi-models.json` from Prism-managed model truth. OpenCode, manual upload enhancement, and platform abstraction are removed. `000027_model_pi_catalog_bindings.sql` is a purely additive migration: one optional `model_pi_catalog_bindings` row per model freezes the selected pi.dev coordinate (`provider_id`, `catalog_model_id`, `api`), a `bind_source` (`single_candidate`/`manual`), the `sha256-…` `catalog_revision` it was bound or last refreshed against, `fetched_at`/`updated_at`, per-field `source_*`/`override_*` pairs for the seven safe leaves `name`/`reasoning`/`input`/`context_window`/`max_tokens`/`thinking_level_map`/`compat`, and sorted `source_dropped_fields` evidence for catalog fields deliberately excluded from Pi output. `000028_model_pi_binding_identity.sql` is a second purely additive, data-preserving migration that adds the non-null `prism_model_id_at_bind` identity snapshot and backfills every retained row from `catalog_model_id`; because the pre-000028 gate forced those two values to be equal, the backfill reproduces each row's real bind-time identity and keeps an already-renamed model drifted instead of silently healing it, and no row is dropped, re-pointed, or rewritten. It is independent of `model_catalog_bindings` (models.dev): neither table reads, rewrites, or reuses the other, and all existing rows survive unchanged.
- The pi.dev client (`internal/domain/pidev`) fetches `https://pi.dev/api/models` outside any transaction: `4 s` timeout, same-origin `https`-only redirects, `16 MiB` budget, `singleflight`, `ETag`/`304` revalidation, last-known-good retention on failure, and `X-Pi-Model-Catalog-Minimum-Version` validation against the pinned `0.84.3` target. The trusted `catalog_revision` is verified as the response body's own SHA-256 (`sha256-…`); a missing or mismatched `X-Pi-Model-Catalog-Revision` header fails the fetch closed and never falls back to the ETag, which is a `304` validator only. Candidates are full `model_id` case-sensitive exact match plus final Pi API compat (`openai-responses`/`openai-completions`/`anthropic-messages`/`google-generative-ai`); no name/slug/host matching, and multiple candidates — even sharing one template — always require an explicit `provider_id`/`catalog_model_id` bind. Separately, `POST /api/models/{model_config_id}/pi/search` is the bounded directory discovery entry for every model whose final Pi API is determinable, including ones the default flow reports as `not_in_catalog` or `api_mismatch`: it is model-id-only, case-insensitive literal containment (never provider, display name, or fuzzy), returns only coordinates carrying exactly that final Pi API, ranks exact/prefix/substring then provider/id over the whole same-API hit set before cutting the `offset` window (offset pages echo their window and the full `total`; a negative offset is a 422), defaults to 20 and clamps to 100, never preselects, publishes the seven safe fields plus dropped paths and the Prism-owned export identity, echoes both `fetched_at` (content download) and `checked_at` (last revalidation, 304 included) so the two stamps stay distinguishable, may serve a last-known-good catalog read-only but always labelled `stale`, and writes nothing.
- `POST /api/models/{model_config_id}/pi/bind` freezes a coordinate after checking the caller's `expected_catalog_revision`, `expected_prism_model_id`, and `expected_pi_api` against a fresh fetch and re-verifying all three under row lock; every rejection writes nothing. An explicit coordinate must be a real entry in the fetched revision carrying exactly the model's current final Pi API, so a deliberate cross-directory `catalog_model_id` is allowed while a cross-API one never is; without explicit coordinates the unchanged 0/1/many exact-candidate flow decides, and the unique candidate still binds as `single_candidate`. The bind also freezes the confirmed Prism identity into `prism_model_id_at_bind`, which is what renderability is compared against — never the directory id. Rebinding to a different coordinate clears prior overrides; repeating the same coordinate with the same confirmed identity is a true no-op so only refresh may advance its frozen source; repeating the same coordinate after a Prism rename preserves frozen source, overrides, revision, `fetched_at` and `bind_source` while advancing the identity snapshot and `updated_at` CAS token. `POST .../pi/refresh/preview` returns a field/dropped-path diff plus coordinate, API, `binding_updated_at`, and catalog-revision tokens; `.../pi/refresh/commit` must match all of them under row lock before replacing only the source fields and dropped evidence, leaving overrides untouched. `PUT`/`DELETE .../pi/override` write and clear sparse per-field manual overrides validated against the bound API's same Pi 0.84.3 schema; `DELETE .../pi` unbinds. The search route plus the six bind/refresh/override/unbind routes are `M2`, planning-neutral, `private, no-store`. `GET /api/models/{model_config_id}/pi` is the single-model Pi management read (`M2`, Default-profile, planning-neutral, `private, no-store`): it publishes the model identity (including Prism's own final `pi_api` mapping), one catalog evidence block (`fresh`/`stale` last-known-good/`unavailable`, with `fetched_at`/`checked_at`), live exact-candidate evidence, and the persisted binding truth (coordinate, frozen `prism_model_id_at_bind`, status, renderability, revision, stamps, source/override/effective, dropped paths) from one read-only `REPEATABLE READ` snapshot plus one shared best-effort catalog fetch; a catalog outage degrades only the live evidence and never manufactures an unbound binding, and the response never carries export targets, pricing plans, source digests, credentials, render results, or any runtime graph.
- `source` does one best-effort live pi.dev fetch for discovery evidence only (`pi_candidates`/`candidate_status`: `not_in_catalog`/`api_mismatch`/`single`/`multiple`/`catalog_unavailable`) and separately reports each model's persisted binding (`pi_selected`, `pi_binding_status`: `unbound`/`bound`/`bound_drifted`, `pi_binding_renderable`, `pi_binding_prism_model_id`, `pi_api`, source/override/effective metadata, and dropped-field evidence), so one row can honestly say `not_in_catalog` and `bound`/renderable at the same time. Live coordinate/template drift is visible but does not invalidate a compatible frozen binding; a Prism full-model-ID or final-Pi-API mismatch sets `pi_binding_renderable=false`. `render` performs no network I/O and reads no live or LKG catalog state: it accepts `expected_source_digest`, `model_config_ids`, `base_url`, `provider_id`, `credential`, and exactly one `selections` coordinate assertion per selected model, each matching its persisted binding, then renders only from the effective frozen fields. The clock-free `source_digest` covers the bound coordinate, its frozen Prism identity snapshot, its revision, effective template, and dropped evidence per model—never the current live-fetch outcome or directory search result. Failures are `409 export_source_stale` on digest drift, `422` on an unbound/incompatible/non-matching selection, and `422`/`409` on bind/refresh conflicts.
- The operator supplies the Prism gateway origin/provider id and chooses whether to omit the client key slot or include a non-empty trimmed typed string; Pi 0.84.3 rejects an explicitly empty `apiKey`, so Prism fails that request with `422 credential_api_key_required`. Export never reads stored upstream endpoint keys and never proxies pi.dev `provider`/`api`/`baseUrl`/`cost`/`headers`/`samplingParams`/`fallback`/`routing` into the file. Price truth comes only from current pricing-template revisions under fail-closed gates, including `pricing_component_missing` when `reasoning_price` or another required component is null; otherwise the model remains and the whole `cost` group is omitted. Safe pi.dev leaves `name`/`reasoning`/`input`/`contextWindow`/`maxTokens`/`thinkingLevelMap`/`compat` are preserved.
- Pricing-template typed cards and peak/valley windows are introduced by `000023_pricing_template_kind_cards.sql` as a fresh-only, destructive shape migration. Before DDL, any retained pricing or currency-migration row raises a readable rebuild-required error; the existing instance must be exported or discarded and restarted with an empty database. This does not waive the backup and explicit-authorization requirement for the retained operating history.
- The running home-LAN instance holds real accumulated operating history. Backing up an instance means `pg_dump` plus a copy of the plaintext config. The database and bootstrap file hold retained product state and are not disposable without backup.

## Compatibility Policy

- Repo convention: when doing upgrade work, prefer clean architecture and the best current implementation over backward-compatibility shims; preserve legacy shapes only when explicitly requested.
- Machine contracts (the operation registry, the file-backed bootstrap v1 schema, the partitioned log-retention tables) evolve within their documented ownership and stay covered by backend regression tests.
- Bootstrap v1 is preserve-only for `runtime.secretEncryptionKey`, parse-only for mail compatibility fields, and restart-required for external file edits.
- The no-shim convention governs code, API, and schema shape. It does not make the running instance's data disposable: a shape change that cannot carry existing data forward needs an explicit decision and a verified backup first.

## Allowed and Prohibited Changes

Allowed:

- Minimal, correct changes within the existing architecture and documented boundaries.
- Clean-architecture-first upgrades per the repo convention, replacing legacy shapes rather than wrapping them in compatibility layers.
- Evolution of existing contracts (operation registry, DB lanes, partitioned retention, durable outboxes) within their documented ownership and with the applicable regression coverage.

Prohibited:

- Destructive data resets or data loss without explicit authorization and a verified backup.
- Deleting, moving, or reorganizing existing documents or machine contracts without explicit authorization.
- External deployment, publication, or release actions without explicit confirmation.
